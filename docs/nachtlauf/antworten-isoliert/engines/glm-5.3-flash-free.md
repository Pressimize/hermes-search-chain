1. **engines.py:70-77 — potenzieller Bug.** Wird eine Nicht-2xx-Antwort erkannt und scheitert danach das Einlesen des Bodys, greift der generische `except Exception`-Zweig und der bereits bekannte HTTP-Status geht verloren. Konkret: `httpx` liest den Body eager vor der Rückgabe; ein `ReadTimeout` beim Nachladen eines 4xx-Bodys wird zu `{"code": "timeout", "status": None}` statt `{"code": "http_402", "status": 402}` — die geplante 24-h-Pause nach HTTP 402 greift dann nicht, obwohl der Server den Status geliefert hat. Beispiel: Firecrawl schickt HTTP 402, aber der Body kommt tröpfelnd. Unerwähnter Nebenaspekt: Exceptions aus `_detail()` (engines.py:46-59) entweichen deren eigenem try-Block (der nur `ValueError`/`RecursionError` um `response.json()` fängt) und landen ebenfalls im generischen Zweig; ob httpx hier z. B. bei defektem gzip/brotli tatsächlich `DecodingError` statt `ValueError` wirft, kann ich bei der httpx-API nicht mit letzter Sicherheit sagen — der strukturelle Punkt bleibt aber bestehen.

2. **engines.py:127 (sowie 35, 119, 146) — Edge Case / Vertragsverletzung.** Der Modulvertrag „Every function ... never raises" (engines.py:3-5) hat Löcher: `min(limit, MAX_RESULTS)` läuft in `parallel()` außerhalb jeder Fehlerbehandlung, und `len(key)` in `_error()` wirft bei `key=None` einen `TypeError`. Beispiel: `engines.parallel(client, "q", "10", "k")` wirft `TypeError` (string + `MAX_RESULTS`), statt ein Fehler-Dict zu liefern. Zusätzlich fehlt für `limit` jede untere Grenze: `limit=0` bzw. `-5` gehen unverändert als `max_results`, `numResults` bzw. Firecrawl-`limit` raus; nur Parallel wird nach oben auf 20 gekappt, Exa/Firecrawl gar nicht.

3. **engines.py:94-104 — Performance.** Es gibt keine Obergrenze für die Anzahl der Ergebniszeilen; `MAX_RESULTS` limitiert nur den gesendeten Request-Parameter (bei Parallel), nicht die Antwort. Ein abweichender oder „kaputter" Provider kann beliebig viele Items liefern, die alle zu Zeilen (je bis 3000/16000 Zeichen description) aufgebaut werden. Beispiel: Firecrawl-Antwort `{"success": true, "data": {"web": [...10^6 Einträge...]}}` erzeugt eine 10^6-Zeilen-Liste und entsprechend hohen Speicher-/CPU-Aufwand in der Funktion, bevor irgendein Limit greift.

4. **engines.py:19-22 mit 67 — Performance/Edge Case.** Der per Request übergebene Timeout gilt laut httpx-Semantik pro Phase; insbesondere läuft der read-Timeout zwischen einzelnen Socket-Reads ab, nicht über die Gesamtdauer. Ein Server, der z. B. alle 9 s ein Byte sendet (Exa: nominell 10 s), löst den Timeout nie aus, obwohl die Gesamtzeit beliebig wächst — in der Suchkette über drei Stufen summiert sich das. Kommentar A0 benennt das Phasenverhalten, aber es fehlt eine absolute Wall-Clock-Deadline (z. B. seitens des Aufrufers mit Abbruch/Deadline).

5. **engines.py:96-104 im Vergleich zu 38 — Security/Einheitlichkeit.** Fehlertexte werden zu einer druckbaren Einzeilendefinition sanitisiert (Control-Zeichen, `\n`, `U+2028` werden ersetzt), aber `title`/`description` der Ergebniszeilen fließen unberührt aus der Provider-Antwort in die Zeilen. Beispiel: Firecrawl-description `"legit\nERROR forged line"` enthält einen Zeilenumbruch — genau dieselbe Log-Forging-Gefahr, gegen die A4 in `_error()` schützt; ein unpaariges Surrogat (z. B. `"\ud800"` in einem Titel, das JSON-dekodiert überlebt) kann zusätzlich beim späteren UTF-8-Schreiben/Loggen der Zeilen crashe. Falls Hermes die Zeilen weiter unten bereinigt, ist die Asymmetrie jedenfalls in den Anhängen nicht erkennbar.

6. **engines.py:35-36 — Security-Edge-Case.** Die Key-Maskierung ist ein exaktes `str.replace` des Rohwerts; ein Provider-Reply, das den Key nicht wörtlich, sondern z. B. URL-encoded (`SECRET%2DKEY`) oder Base64-kodiert zurückspiegelt, wird nicht maskiert und landet im (gekürzten) Fehlertext. Beispiel: key `SECRET-KEY`, Reply-Text `invalid key: SECRET%2DKEY` → `["error"]` enthält die kodiert VERSION unverdeckt. Das ist eine bewusst einfache Heuristik (S3), aber ich kann aus den Anhängen nicht ablesen, ob reale Provider so kodiert echo'en — als harte Guarantee sollte S3 dann nicht gelesen werden.

7. **engines.py:70 — Abweichung von Best Practices.** Bei Fehlern wird nur `status`, `code` und der aufbereitete `detail` weitergegeben; die Response-Header (insbesondere `Retry-After`) werden verworfen. Die beschriebene Pausenlogik pausiert nach HTTP 429 fix 60 s — wenn der Anbieter z. B. `Retry-After: 300` schickt (Beispiel: Firecrawl-Antwort HTTP 429 mit diesem Header), wird der Hinweis ignoriert und erneut versucht; HTTP sieht das Honorieren von `Retry-After` als korrektes Verhalten vor. An der konkret gezeigten Codestelle (Return in `_post`) ginge der Header unstere bezogenen Informationen verloren.
