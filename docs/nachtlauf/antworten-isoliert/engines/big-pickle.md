1. **engines.py:39** — Kategorie: potenzieller Bug. `ERROR_MAX` begrenzt nur den Detailteil, das Präfix `"{provider}: "` kommt obendrauf, der zurückgegebene Fehlertext ist also 200 + len(Präfix) Zeichen lang (Firecrawl: 211). Die Zweckbeschreibung verlangt einen auf 200 Zeichen gekürzten Fehlertext, und test_engines.py:263 zementiert das Gegenteil (`len(f"{name}: ") + 200`). Beispiel: Exa antwortet 401 mit `{"error": "x"*500}` → `out["error"]` ist 205 Zeichen lang.

2. **engines.py:127** — Kategorie: potenzieller Bug. `MAX_RESULTS` wird nur in `parallel` angewandt; `exa` (Zeile 119) und `firecrawl` (Zeile 146) schicken `limit` unbegrenzt an die API. Die Konstante ist generisch benannt (nicht `PARALLEL_MAX`), nur test_engines.py:160 prüft den Cap, sodass die Lücke in der Suite nicht auffällt. Beispiel: `call(engines.exa, handler, "q", 50, "k")` → der Request enthält `numResults: 50`, Firecrawl entsprechend `limit: 50`.

3. **engines.py:92** — Kategorie: Edge Case, der zu Fehlverhalten führt. Ein einziges Nicht-Dict-Item in der Liste verwirft die *gesamte* Antwort als `malformed`, obwohl die übrigen Einträge gültig wären; dass Items sonst bewusst nachlässig behandelt werden (URL-Filterung Zeile 94), zeigt die Inkonsistenz. Die Suite testet nur rein defekte Listen (test_engines.py:249-250), nicht Mischungen, das Verhalten ist also nicht abgedeckt. Beispiel: `{"results": [{"url": "https://a.example/", "title": "A"}, "junk"]}` → `{"error": "Exa: malformed reply"}` statt einer Zeile.

4. **engines.py:96-104** — Kategorie: Security. Die Key-Maskierung gibt es ausschließlich in `_error` (Zeile 35); Zeilen aus `_rows` werden unverändert zurückgegeben. Erhält ein Anbieter den Key in `title`, `description` oder `highlights` zurück, steht er unmaskiert im Ergebnis und damit im Log/Kontext der Kette. Beispiel: key `exa-key-12345678`, Reply `{"results": [{"url": "https://a.example/", "highlights": ["x-api-key: exa-key-12345678"]}]}` → die Description enthält den Key im Klartext.

5. **engines.py:35-36** — Kategorie: Security. `str.replace` ist exakt und case-sensitiv; jede Transformation des gespiegelten Keys umgeht die Maskierung. Beispiel: key `AbC-12345678`, der Anbieter spiegelt `abc-12345678` oder `AbC-12345678` mit eingefügtem Zeilenumbruch → erscheint unmaskiert in `out["error"]`. Ob einer der drei Anbieter den Key tatsächlich so transformiert, kann ich nicht sicher sagen; die Lücke in der Implementierung ist aber belegt.

6. **engines.py:151** — Kategorie: Edge Case, der zu Fehlverhalten führt. `data.get("success") is not True` ist strenger als eine Wahrheitsprüfung: JSON-Wert `1` (statt `true`) führt zu `malformed`, obwohl `data.web` gültige Treffer enthält. Beispiel: `{"success": 1, "data": {"web": [{"url": "https://a.example/"}]}}` → `{"error": "Firecrawl: malformed reply"}` statt einer Zeile.

8. **engines.py:100 (mit 111)** — Kategorie: Performance. `text(item)` verbindet alle `highlights` bzw. `excerpts` unbegrenzt zu einem String, erst danach wird auf 16.000 Zeichen geschnitten. Beispiel: 20 Exa-Ergebnisse mit je 1 MB Highlights → ~20 MB Zwischenstring, von denen am Ende 20 × 16.000 Zeichen bleiben.

9. **engines.py:39** — Kategorie: Edge Case, der zu Fehlverhalten führt. Nach dem Maskieren kann `[key]` durch `text[:ERROR_MAX]` angeschnitten werden, sodass ein Fragment (`[ke`) stehen bleibt. Beispiel: key `SECRET-KEY-0123456789`, Vendor-Detail `"y"*188 + key + "z"*10`, Antwort 401 → `out["error"] == "Exa: HTTP 401 " + "y"*188 + "[ke"`.
