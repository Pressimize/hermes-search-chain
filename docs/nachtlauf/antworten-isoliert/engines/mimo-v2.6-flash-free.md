1. **engines.py:121 und 140 — potenzieller Bug.** Ein 2xx-Reply, dessen Body eine Fehlermeldung statt `results` enthält, wird als „keine Treffer" behandelt: `data.get("results")` ist `None`, `_rows` liefert `{"rows": []}` und der Fehlergrund ist verschwunden (Firecrawl prüft zumindest `success`, 151–153). Die Kette hält das dann für eine Treffer-freie Stufe und geht zur nächsten weiter, statt den Fehler zu melden. Beispiel: HTTP 200 mit `{"error": "quota exceeded"}` an Exa → Ausgabe `{"rows": []}`.

2. **engines.py:151–153 — Edge Case, der zu Fehlverhalten führt.** Bei HTTP 200 mit `{"success": false, "error": "Payment Required: Insufficient credits"}` gibt es zwei Verluste: `_malformed` verwirft den Anbieter-Grund, den `_detail` (46–59) bei Nicht-2xx gerade explizit aus `error`/`message` holen würde, und `status` wird `None`. Damit ist die im Zweck genannte Pause (24 h nach HTTP 402) über diesen Pfad nicht auslösbar. Beispiel: `{"success": False, "error": "Payment Required: Insufficient credits"}` als 200er → `{"error": "Firecrawl: malformed reply", "status": None}`; das aktuelle Verhalten ist in test_engines.py:186–189 festgelegt.

3. **engines.py:87 und 116 — Abweichung von Best Practices.** `text_max: int = TEXT_MAX` und `highlight_chars: int = EXA_HIGHLIGHT_CHARS` werden als Default-Argumente zur Importzeit gebunden, alle übrigen Konstanten (`ERROR_SCAN`, `ERROR_MAX`, `TITLE_MAX`, `FIRECRAWL_TEXT_MAX`) dagegen zur Laufzeit aus dem Modul- namespace gelesen. Das macht die Konstanten inkonsistent konfigurierbar: `monkeypatch.setattr(engines, "TEXT_MAX", 100)` oder `...("EXA_HIGHLIGHT_CHARS", 50)` ändert an Exa/Parallel nichts mehr, während `monkeypatch.setattr(engines, "FIRECRAWL_TEXT_MAX", 100)` (expliziter Argumentwert, 153) und `ERROR_SCAN` (test_engines.py:292) wirken.

4. **engines.py:99–100, 111, 153 — Security (eingeschränkt).** `url`, `title` und `description` werden nur auf Länge begrenzt, nie auf druckbare Zeilenzeichen geprüft, obwohl der Fehlerpfad (engines.py:38) genau das als A4 verlangt. Neu-/Steuercodes aus der Anbieterantwort gehen unverändert in die Ergebniszeilen. Beispiel: `{"results": [{"url": "https://a.example/\u001b[2J", "title": "A\u0007", "highlights": ["ok\nFORGED"]}]}` → sämtliche Zeichen bleiben erhalten. Kritisch wird das erst, wenn Hermes die Zeilen roh in Log/Terminal schreibt (JSON-Serialisierung escaped Steuerzeichen als `\u001b`); das ist aus den Anhängen nicht erkennbar.

5. **engines.py:119, 127, 146 — Edge Case, der zu Fehlverhalten führt.** `MAX_RESULTS = 20` wird nur in `parallel` (127) angewandt; Exa bekommt `numResults: limit` und Firecrawl `limit: limit` ungekappt, obwohl die Konstante global neben den Timeouts steht. Bei einem großen `limit` verhalten sich die drei Stufen also unterschiedlich. Beispiel: `exa(client, "q", 5000, "k")` → Body `{"numResults": 5000}`, `parallel(client, "q", 5000, "k")` → `{"max_results": 20}`. Unsicherheit: Ob A6 nur Parallel meint, geht aus dem Code nicht hervor, und die realen Höchstwerte von Exa/Firecrawl kenne ich nicht.

6. **engines.py:59, 67 — Performance.** `client.post(...)` liest die Antwort vollständig in den Speicher (kein Streaming, keine Größenbegrenzung), danach erzeugt `response.text.strip()` eine zweite vollständige Kopie und `_error` (38) liefert `str.replace(key, …)` über den ganzen Text, obwohl nur `ERROR_SCAN = 2000` Zeichen verwendet und 200 behalten werden. Beispiel: 402-Antwort mit 50 MB Text → mehrere 50-MB-Strings im Speicher. Ein früheres Abschneiden ist allerdings nicht trivial, weil test_engines.py:290–297 fordert, dass die Key-Maskierung den gesamten Body sieht.

7. **engines.py:100 mit 111 — Performance.** `text(item)` (`" ".join` über alle `highlights`/`excerpts`) baut die komplette Beschreibung, bevor `[:text_max]` greift; das Limit begrenzt also nur die Ausgabe, nicht den Aufwand. Beispiel: Exa liefert 8 Highlights à 1 MB → ~8 MB werden verkettet, dann auf 16.000 Zeichen verworfen. Dasselbe gilt für `title` (99) bei extrem langen Titeln.

8. **test_engines.py:244–255 — schlechter Stil.** Die vier `httpx.Response(...)`-Objekte werden beim Import der Datei erzeugt und dieselbe Instanz für die Parametrisierungen „Exa", „Parallel" und „Firecrawl" wiederverwendet; httpx hängt an jeder Nutzung das jeweilige `request` an, der Zustand wandert also zwischen den Läufen. Aus dem Code ist keine aktuelle Fehlfunktion ableitbar (es wird nur `out` geprüft), aber ein späterer Zusatz wie `response.request.url`-Assertions würde je nach Parametrisierungsreihenfolge falsch greifen. Hilfreich wäre ein Factory-Lambda wie `reply()` (Zeile 26), das pro Aufruf ein frisches Objekt baut.
