1. **search_chain/engines.py:119,146 (potenzieller Bug / Abweichung von der Spezifikation)** — Die Obergrenze `MAX_RESULTS` (20) wird nur in `parallel` (Zeile 127) angewandt, nicht in `exa` (`"numResults": limit`) und `firecrawl` (`"limit": limit`). Laut Design A1/A3/A6 soll „at most 20“ im Request-Body stehen; aktuell hält nur `provider.py:106` die Grenze ein, der Engine-Aufruf selbst ist ungeschützt. Beispiel: `engines.exa(client, "q", 100, "k")` sendet `numResults: 100` (verifiziert), `engines.firecrawl(..., "q", 100, ...)` sendet `limit: 100`; die Suite testet den Cap nur für Parallel (`test_parallel_caps_results_at_20`).

2. **search_chain/engines.py:127 (Edge Case)** — `min(limit, MAX_RESULTS)` hat keine Untergrenze und keine Typ-Prüfung; `engines.parallel(client, "q", 0, "k")` sendet `"max_results": 0` (verifiziert), negative Werte werden negativ. Über `provider.py:106` (`max(1, ...)`) ist das derzeit nicht erreichbar, aber die Engine-Funktion ist allein nicht A6-konform und würde einen ungültigen Body erzeugen.

3. **search_chain/engines.py:33-38 (potenzieller Bug / Vertragsbruch)** — Der Modul-Docstring (Zeile 3-4) und die Design-Notizen sagen „wirft nie“, aber `_error` ruft `len(key)` (Z. 35) und `text.replace(key, ...)` (Z. 36) auf, ohne den Typ zu prüfen. `engines.exa(client, "q", 5, None)` bzw. `b"12345678"` löst eine `TypeError` aus (verifiziert: `object of type 'NoneType' has no len()` / `replace() argument 1 must be str`). Über `provider.py` kommt immer ein `str` an, daher niedrige Schwere, aber der zugesicherte „never raises“-Vertrag gilt für die Engine-API nicht.

4. **search_chain/engines.py:52-58 (schlechter Stil / Edge Case)** — `_detail` macht `str(value)`, wenn `error`/`tag`/`message` kein String ist; dadurch landen Python-Repräsentationen im nutzersichtbaren Fehlertext. Beispiel: HTTP 400 mit `{"error": ["a","b"]}` ergibt `"Exa: HTTP 400 ['a', 'b']"` (verifiziert); ein `{"error": {"type": "billing"}}` ohne `message` fällt bis auf `response.text` durch und liefert das rohe JSON statt einer Meldung.

5. **search_chain/engines.py:92-94 (Edge Case)** — Ein einziges Nicht-Dict-Element in `results`/`web` lässt `_rows` die gesamte Antwort als `malformed` verwerfen, während ein Element mit ungültiger URL (Z. 94) einzeln entfernt wird. Beispiel: `{"results": [{"url": "https://a/", "highlights": ["x"]}, "noise"]}` ergibt `{"error": "Exa: malformed reply"}` (verifiziert), obwohl ein brauchbarer Treffer vorhanden war; die Kette geht dann zur nächsten Stufe. Das kann gewollt sein (K4, `test_malformed_reply`), aber die Asymmetrie zur URL-Filterung sollte bewusst entschieden sein.

6. **search_chain/engines.py:76-77 (Abweichung von Best Practices)** — Das blanke `except Exception` ersetzt die Originalausnahme durch nur `type(exc).__name__` und verwirft Traceback und Meldung. Ein echter Programmierfehler (z. B. geänderte `httpx`-Signatur, `TypeError` beim Header-Bau) sieht damit im Log exakt wie ein Transportfehler aus und ist nicht diagnostizierbar; die Fehlermeldung `"ConnectError"` ist zudem kein stabiler, namespaced Code.

7. **tests/test_engines.py:317 (schlechter Stil / fragiler Test)** — `test_timeouts_are_passed_to_httpx` liest `request.extensions["timeout"]`, eine interne `httpx`-Struktur; ändert `httpx` deren Layout, schlägt der Test fehl, ohne dass das Produkt falsch ist. Ein Test über einen injizierten Transport/`httpx.Timeout` oder über das beobachtbare `ReadTimeout` wäre robuster.
