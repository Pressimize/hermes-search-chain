1. **provider.py:108 — Performance / Abweichung von Best Practices.** `search()` erzeugt bei jedem Aufruf einen neuen `httpx.Client`. Connection-Pooling und Keep-alive gehen damit komplett verloren: Nach jeder Suche (`finally` schließt den Client) werden bei der nächsten Suche TCP+TLS neu aufgebaut, bei einer Fallback-Kette bis zu dreimal pro Aufruf. Hermes registriert den Provider einmalig (siehe `__init__.py:6`), ein instanzweit wiederverwendeter (lazy erzeugter) Client wäre hier der übliche Ansatz; der `transport`-Parameter für Tests stünde dem nicht im Weg.

2. **provider.py:106 — Edge Case.** `limit` wird nur geklemmt, aber nicht validiert oder zu `int` gezwungen. Konkrete Beispiele: `search("q", None)` bzw. `search("q", "10")` lösen in `min()` einen `TypeError` aus — die komplette Suche scheitert mit „search-chain: TypeError", obwohl alle Stufen laufen könnten; `search("q", 7.5)` überlebt das Klemmen und ein Float landet als `numResults: 7.5` bzw. `limit: 7.5` im Request-Body (ob Exa/Parallel/Firecrawl das akzeptieren, kann ich ohne engines.py nicht sagen). Dass Hermes Werte unvalidiert durchreicht, nimmt der Code für `query` selbst an (Kommentar Zeile 103) — dieselbe Argumentation gilt für `limit`, das nur bei int-Typ funktioniert.

3. **conftest.py:44 — Abweichung von Best Practices (Testumgebung).** `sys.modules["agent.web_search_provider"]` wird bedingungslos überschrieben, während `"agent"` in Zeile 43 via `setdefault` geschützt wird. Wenn das echte Hermes im selben Test-Venv installiert ist, ersetzt das Importieren dieses conftest (Collection-Zeit) das echte Modul für die gesamte pytest-Session und kann Hermes-eigene Tests im selben Lauf kontaminieren. Der Kommentar verspricht „Stand-in … so the plugin imports without Hermes installed" — ein Guard (z. B. `setdefault` oder nur injizieren, wenn das echte Modul nicht importierbar ist) wäre konsistent.

4. **provider.py:35-36 — Abweichung von Best Practices.** `_env()` verschluckt jede `Exception` stillschweigend. Ein echter Programmfehler in der Hermes-Umgebung (z. B. ein durch ein Hermes-Update geändertes `get_provider_env`, das `TypeError` wirft) ist damit vom „Key nicht gesetzt" nicht unterscheidbar: Die Stufe wird stillschweigend als `no_key` übersprungen, ohne jeden Log-Eintrag. Weniger pauschalesfangen oder zumindest ein `log.debug` mit dem Ausnahmetyp würde die Diagnose erleichtern.

5. **provider.py:96-98 und 124/132-133 — schlechter Stil (Diagnosierbarkeit).** Löst ein Stufenaufruf eine unerwartete Exception (Zeile 124, nicht von engines gefangen), wird (a) für diese Stufe kein `steps`-Eintrag angehängt — der `finally`-Log zeigt eine scheinbar kürzere Kette, z. B. „search-chain: exa=empty", obwohl Parallel gecrasht ist — und (b) verwirft der Rückgabewert in Zeile 98 alle bis dahin gesammelten `reasons`: Das Modell sieht nur die Ausnahmeklasse ohne jeglichen Kettenkontext. Genau dieses Verhalten codifiziert test_provider.py:391-398; beide Punkte ließen sich mit einem `try/except` um `call()` (steps-Eintrag `parallel=crash` + `reasons` verwenden) beheben.

6. **provider.py:118-135 — Performance (gering).** Einträge in `self._paused` werden in Zeile 135 gesetzt, aber nie entfernt; abgelaufene Pausen bleiben für die Lebensdauer des Prozesses liegen. Bei häufig wechselnden Keys (Profilwechsel, korrigierte Keys — das eigentliche Ziel von K5, siehe test_provider.py:238-244) wächst die Tabelle unbegrenzt. In der Praxis klein, aber kostenlos unasufhaltsam vermehrbar; ein Verwerfen abgelaufener Einträge beim Lookup wäre trivial.

7. **provider.py:112 — schlechter Stil (gering).** `{"success": False, "error": "Interrupted"}` ist die einzige `_failed`-Rückgabe ohne das Präfix „search-chain:" (Vergleich Zeile 98, 105 und das Join in Zeile 138). Falls Hermes die Meldung nicht schon als Unterbrechungs-Signal erkennt (Konvention laut Kommentar zu Zeile 23 — das kann ich ohne Hermes-Quellcode nicht prüfen), fehlt dem Fehtext die Provider-Zuordnung.
