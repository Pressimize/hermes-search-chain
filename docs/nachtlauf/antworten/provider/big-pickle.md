1. **Datei:** `.opinion/provider.py`, **Zeile:** `60`  
   **Kategorie:** potenzieller Bug  
   **Begruendung:** Die Funktion `_left` rundet bei >= 3600 s mit `math.floor(seconds/3600 + 0.5)` (klassisches Round-Half-Up auf Stunden). In den Testfällen zu `test_remaining_pause_in_the_error_text` wird erwartet, dass z. B. nach 81000 s seit Start (Clock.now=1000, Pause 86400 s bis 87400, also Rest 6400 s? 87400−(1000+81000)=6400 s = 1h46m) der Text `(paused for another 2 h)` lautet (Testzeile ~298–299: `(81000, "2 h")`). Tatsächlich wird 6400/3600=1.777…, +0.5=2.277…, floor=2 – das passt. Ebenso 81001 s -> Rest 6399 s = 1h46m59s -> 1.777? 6399/3600=1.7775, +0.5=2.2775, floor=2. Der Test erwartet aber `(81001, "1 h")` (Zeile ~300). Genau dieser Sprung von 81000 auf 81001 erwartet also einen Wechsel von "2 h" auf "1 h", obwohl die verbleibende Zeit nur um 1 s sinkt. Das ist ein Rundungsartefakt der Stundenrundung (1h46m wird zu 2h gerundet, 1h45m59s ebenfalls zu 2h gerundet, aber der Test erwartet hier offenbar "1 h"). Ohne Kenntnis der beabsichtigten Rundungsregel (z. B. round-to-nearest-hour mit Floor statt Round-Half-Up oder Abrunden auf volle Stunden ab bestimmter Schwelle) ist diese konkrete Erwartung im Widerspruch zur implementierten Formel.  
   **Konkretes Eingabe-Beispiel:** `clock.now = 1000 + 81001`, Pause läuft bis 87400 -> Rest 6399 s; `_left(6399.0)` ergibt `"2 h"` nach aktueller Implementierung, Test erwartet jedoch `"1 h"`.  

2. **Datei:** `.opinion/provider.py`, **Zeile:** `118`  
   **Kategorie:** potenzieller Bug  
   **Begruendung:** Für den Pausenschlüssel wird `hashlib.sha256(key.encode("utf-8", "surrogatepass")).hexdigest()` verwendet. Der Test `test_key_that_cannot_be_encoded_fails_only_its_stage` setzt `env["EXA_API_KEY"] = "k\ud800y12345"` (lone surrogate). Mit `surrogatepass` werden lone Surrogate durch Ersatzcodeeinheiten kodiert, sodass Bytes entstehen und SHA-256 definiert berechenbar ist. Das ist konsistent zum Testziel ("does not stop the chain"). Allerdings ist unklar, ob Hermes-Keys jemals solche Zeichen enthalten können; die gewählte Kodierung ändert den Digest gegenüber einer "normalen" UTF-8-Kodierung. Falls ein echter Key versehentlich einen lone surrogate enthielte (z. B. durch Environment-Mapping), wäre der Slot ein anderer als beabsichtigt. Der Codebezug ist konkret, aber ohne Kenntnis der httpx/Hermes-Umgebung kann ich nicht sicher sagen, ob das ein reales Fehlverhalten auslöst.  
   **Konkretes Eingabe-Beispiel:** `env["EXA_API_KEY"] = "k\ud800y12345"`, dann `SearchChainProvider().search("q")` – Test erwartet, dass Exa übersprungen wird und Parallel bedient (Stage wird nicht blockiert).  

3. **Datei:** `.opinion/provider.py`, **Zeile:** `120–123`  
   **Kategorie:** Edge Case, der zu Fehlverhalten fuehrt  
   **Begruendung:** Die Pause wird nur aktiv, wenn `(left := until - self._clock()) > 0`. Bei exakter Gleichheit (`left == 0`) wird der Slot nicht als pausiert behandelt und die Stage wird erneut versucht. Das ist ein klarer Grenzfall (Boundary). Die Tests decken ihn implizit ab (z. B. `after == 82800` ergibt laut Test noch "1 h" im Fehlertext beim zweiten Aufruf, aber der zweite Aufruf findet nach erneutem Zeitablauf statt). Ob das gewünschte Verhalten ist (Pause endet exakt zum Zeitpunkt `until`), ist aus dem Code ersichtlich; problematisch wird es nur, wenn `clock()` jemals nicht monoton steigt oder Rundungsfehler auftreten. Codebezug ist eindeutig.  
   **Konkretes Eingabe-Beispiel:** `clock.now = 1000`, Exa liefert 402 -> `until = 1000+86400=87400`. Setze `clock.now = 87400`: Bedingung `87400-87400 > 0` ist False -> Exa wird erneut angefragt (kein `paused`-Schritt).  

4. **Datei:** `.opinion/provider.py`, **Zeile:** `134–137`  
   **Kategorie:** potenzieller Bug  
   **Begruendung:** Beim Setzen der Pause wird `detail = result["error"].partition(": ")[2]` extrahiert und nur dieser Teil im WARNING-Log ausgegeben (`"search-chain: %s paused for %d s (%s)"`, Zeile 137). Der gespeicherte `reason` in `_paused` ist jedoch der komplette `result["error"]` (Zeile 135). Im Fehlertext des zweiten Aufrufs erscheint dann wieder der komplette Fehler (`f"{reason} (paused for another {_left(left)})"`, Zeile 122). Das ist inkonsistent zwischen Log (nur Detail nach ": ") und zurückgegebenem Fehlertext (kompletter Grund). Zudem hängt das Log-Detail davon ab, ob der Fehlerstring genau `": "` enthält. Wenn der Fehler aus Engines kommt, ist das vermutlich so; ohne Engines-Implementierung kann ich nicht ausschließen, dass bei bestimmten Fehlermeldungen das Detail leer oder irreführend ist.  
   **Konkretes Eingabe-Beispiel:** `exa` liefert `{"status":402,"code":"http_402","error":"Exa: HTTP 402 NO_MORE_CREDITS"}` -> Log enthält `(... (HTTP 402 NO_MORE_CREDITS))`, zweiter Aufruf enthält kompletten String. Funktioniert wie getestet, aber die Trennung ist fragil.  

5. **Datei:** `.opinion/provider.py`, **Zeile:** `103–106`, `124–131`

   **Begruendung:** `limit` wird auf `[1, engines.MAX_RESULTS]` geclamppt (Zeile 106), aber nirgends geprüft, ob `limit` ein int ist. `search` akzeptiert `limit: int = 5` (Zeile 92), doch der frühe Check prüft nur Query-Typ (Zeile 103).    **Konkretes Eingabe-Beispiel:** `provider.search("q", limit=None)` oder `provider.search("q", limit=5.5)`.  

6. **Datei:** `.opinion/provider.py`, **Zeile:** `95–101`  
   **Kategorie:** Abweichung von Best Practices  
   **Begruendung:** `search` fängt `Exception` breit ab (Zeile 96–99), loggt nur `type(exc).__name__` und gibt generischen Fehler `"search-chain: {Typ}"` zurück. Gleichzeitig wirft `_chain` nie (laut Aufgabenstellung), aber der äußere Catch deckt z.    **Konkretes Eingabe-Beispiel:** Jeder nicht antizipierte Fehler in der Kette (z. B. fehlerhafte Engines-Rückgabe) wird auf Typnamen reduziert.

10. **Datei:** `.opinion/conftest.py`, **Zeile:** `34–38`  
    **Kategorie:** potenzieller Bug  
    **Begruendung:** `get_provider_env` strippt den Rückgabewert (`return str(value).strip()`), aber in `provider.py` wird `_env` in `_exa`/`_parallel` direkt ohne Strip verwendet (Zeilen 40, 47). Das kann zu abweichendem Verhalten zwischen Tests (mit conftest) und echter Hermes-Umgebung führen. Codebezug ist konkret zwischen conftest und provider.  
    **Konkretes Eingabe-Beispiel:** In Umgebung steht `SEARCH_CHAIN_EXA_HIGHLIGHT_CHARS=" 1200 "`. Mit conftest-`get_provider_env` würde der Provider via `_env` (Zeile 34–37 in provider nutzt `get_provider_env`) tatsächlich `"1200"` erhalten – das hängt davon ab, ob in echter Umgebung `get_provider_env` strippt. In provider.py:34–37 ruft `get_provider_env(name)` auf; conftest definiert genau dieses mit `.strip()`. Also im Testkontext wird bereits gestrippt – Befund 8/9 wären im Testkontext nicht sichtbar? Im Test wird `env[...] = value` direkt in conftest.ENV gesetzt und `get_provider_env` liest daraus und strippt. Provider ruft `get_provider_env`, also erhält er bereits `"1200"`. Die Tests erwarten also, dass `get_provider_env` strippt – was conftest tut. Die provider-eigenen Checks in Zeile 41–42 (`isascii`, `isdecimal`, `len`) prüfen dann den bereits gestrippten Wert. Damit passt `" 1200 "` via conftest zu 1200. Befund 8/9 sind also eher gegen den reinen Wortlaut des provider-Codes gerichtet, aber im Zusammenspiel mit `get_provider_env` (wie in conftest/Hermes) wird whitespace-normalisiert. Trotzdem ist der Code in provider.py ohne Strip inkonsistent zu dem, was Tests erwarten.
